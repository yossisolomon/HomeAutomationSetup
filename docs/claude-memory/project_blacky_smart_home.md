## Home Assistant ops (headless, no UI/token)

- HA repo on blacky: `~/homeassistant/`. Config `config/`, Z2M data `zigbee2mqtt/data/`. Tracked
  config files are `yossi:yossi` (git-pullable). Entity registry: `config/.storage/core.entity_registry`
  — resolve real device entity ids here (Xiaomi MIoT `xiaomi_sg_<deviceid>_cpa4_*` / zhimi `vb4`, Z2M `binary_sensor.<friendly>_contact`).
- **No HA API token** → can't call services / read live state via REST. Read state via
  `config/.storage/core.restore_state` (RestoreEntity-backed only; rewritten periodically → often
  **stale right after a restart**) or MQTT retained `mosquitto_sub -h localhost -t 'zigbee2mqtt/#' -v -W 5`
  (broker `allow_anonymous true`). Service calls / reloads (`automation.reload`, helper toggles) = **user does in Dev Tools UI**.
- Validate config: `make check` (= `docker exec homeassistant python -m homeassistant --script check_config -c /config`).
  Exit 0 + no error lines = valid (prints little on success). Does NOT verify entity existence (runtime).
- `docker restart homeassistant` reloads ALL config but leaves Z2M + mosquitto up → Zigbee contacts
  recover last state via **retained MQTT** on reconnect (no need to physically open/close after an HA-only restart).
- blacky `python3` lacks `yaml` module (use `json`/`grep`); `jq` not installed.
- Change flow: edit on Mac → **PR + green CI → squash-merge** to `origin/main` (main is branch-protected,
  no direct push) → `ssh blacky "cd ~/homeassistant && git pull --ff-only origin main"` (verify clean tree first).

## CUPS Print Server (HL-1110)

- Brother **HL-1110** (USB `usb://Brother/HL-1110%20series`), system default dest. Server-side filtered: queue uses brlaser PPD (`/etc/cups/ppd/HL-1110.ppd` → `rastertobrlaser` filter present). **Not a raw queue.**
- Web UI: `http://192.168.1.222:631` (or `blacky.local:631`). Advertised via Avahi/Bonjour (mDNS 5353) → Macs discover automatically.
- **Admin login = Linux user `yossi` + Linux password** (PAM, `/etc/pam.d/cups`). NOT `yossi_solomon` (that's only the Mac job-owner string; no such linux user). `yossi` ∈ `lpadmin`+`sudo`; `SystemGroup root lpadmin` → authorized. Verified working 2026-06-27 (earlier failure was a mistyped password).
- Cancel own stuck job over SSH (no 631 auth, no sudo — owner match): `ssh blacky "cancel <job-id>"` / `cancel -a HL-1110`. Queue: `ssh blacky "lpstat -t"`.
- error_log/ppd/cupsd.conf are **root-only** → Claude sudo-over-ssh blocked, user runs `sudo tail -30 /var/log/cups/error_log` (or view in 631 UI).
- **"Filter failed" from Mac:** Mac using a Brother-specific driver renders to Brother format, then blacky re-filters with brlaser → input mismatch → fail (double-filter). Fix: on Mac add the Bonjour queue with **Generic PostScript / AirPrint (IPP Everywhere)**, not the Brother driver — Mac sends PDF, blacky does brlaser→USB.

## Battery / UPS (ThinkPad internal pack)

- Pack = SANYO 92P1137, **mfd 2013, 132 cycles, ~82% health** (58.4/71.3 Wh). Fuel gauge **chronically unreliable**: `remaining_percent_error ≈ 25`. It can **freeze its reported % at the TLP START threshold (70) for weeks** while real charge drains — TLP only recharges when reported %<START, so a stuck reading blocks recharge → silent drain to empty (this caused the "battery down while on AC" incident).
- Fix (live since 2026-06-23, setup.sh §3d): **`battery-gauge-refresh.sh` + systemd timer daily 08:00** — briefly raises `start_charge_thresh` to 90 to force a short charge, which re-syncs the gauge + reveals true %, then `trap` restores 70/80. Publishes `thinkpad_battery_gauge_refresh_percent` (the *trustworthy* reading), `_timestamp_seconds`, `remaining_percent_error`, `cycle_count`. Live capacity gauge (`thinkpad_battery_capacity_percent`) is **advisory only**.
- Grafana alerts: `blacky_battery_true_low` (daily probe <40%), `blacky_gauge_refresh_stale` (>48h), `blacky_battery_health_low` (<50% design Wh). Dashboard `grafana/dashboards/blacky-battery.json` (uid `blacky-battery`).
- **On-battery shutdown sequence (live 2026-06-24):** udev `99-power.rules` → AC-loss runs `on-battery.sh` (arms 1h `battery-shutdown-timer` + a `battery-shutdown-warn` timer at T+55m); AC-restore runs `on-ac.sh` (cancels both). The 1h guard is **time-based, gauge-independent** — it fired correctly during an unplug test despite the lying gauge (shut down at the 1h mark; no low-% alert because % never dropped). Telegram across the whole sequence via `/usr/local/bin/notify-telegram.sh` (Bot API, creds from `config/secrets.yaml` `telegram_bot_token`/`telegram_chat_id`): AC-lost CTA → 5-min warning → shutting-down-now (both 1h-timer and `<=20%` watchdog paths) → restored/cancelled.
- **Boot-recovery gotcha:** both shutdown paths (`shutdown-if-on-battery.sh`, `battery-watchdog.sh`) run `docker stop` before poweroff → containers marked explicitly-stopped → `restart: unless-stopped` will **NOT** auto-start them on next boot (stack stays dead until manual `up`). Fixed by `homeassistant-stack.service` (boot oneshot, runs as `yossi`, `docker compose up -d`).
- **OS-unit deploy path:** `cd_deploy.py` only applies HA-relevant changes (`config/`, compose) — it pulls OS-level systemd units/scripts but **never installs them**. Canonical idempotent installer = `scripts/apply-power-units.sh` (setup.sh §3c calls it); re-apply on a running blacky with `ssh blacky 'sudo bash ~/homeassistant/scripts/apply-power-units.sh'` (needs root; Claude's sudo-over-ssh is hard-blocked → user runs it). `cd_deploy.py` now Telegrams on the `none` path too (previously silent → that was why OS/infra deploys went unnotified).
- **node_exporter gotcha:** `--collector.powersupply.ignored-supplies=^BAT0$` only filters metric *export* — the collector still *reads* BAT0 sysfs, and reading the T400's phantom `charge_*_threshold` files triggers ~24/min `thinkpad_acpi BCSG/BCTG AE_NOT_FOUND` kernel-log spam. To actually stop the reads use **`--no-collector.powersupplyclass`** and republish needed values (capacity/health Wh/`blacky_ac_online`) via the textfile collector (`ha-battery-metrics.sh`). rsyslog can't help — spam lands only in the journal via `/dev/kmsg`.
